# 記事生成成果物 評価設計書

作成: AIデザイナー
作成日: 2026-05-07
対象: `articles` テーブルに保存される全記事（articleType: client / interviewer / conversation、volume: short / medium / long / pillar）
運用担当: レビュアー

関連: `docs/review-log/ai-cast-evaluation.md`（インタビュー評価）と並走する記事評価。AIキャストの取材品質を見るのが前者、書き出された記事の品質を見るのが本書。

---

## この文書の目的

記事生成（`app/api/projects/[id]/article/route.ts`）の出力品質を、定期的・継続的に確認し改善するための評価基準と運用手順を定める。

設計の初版は AIデザイナー が書き、以後の運用・改訂は レビュアー が主担当となる。AIセルフ採点（`articles.quality_review.ai_self`）も本ルーブリックを参照する形で実装する。

---

## 1. 評価の対象と目標

### 評価する成果物

1本の記事を「1件の評価単位」とする。評価対象は以下の3点。

| 対象 | 概要 |
|---|---|
| 内容の質 | 一次情報の密度、抽象表現の少なさ、視点の一貫性 |
| 構造の質 | タイトル・抜粋・見出し・CTA・内部リンクの設計 |
| 形式の遵守 | 一人称統一、文字数遵守、形式ルール |

### 評価の目標

- 記事タイプ（client / interviewer / conversation）ごとの強みと弱点パターンを把握する
- 「何を改善すれば価値が上がるか」をプロンプト改善に繋げる
- Gate A（ブログのブランディング水準）の判定材料として使う

---

## 2. 評価ルーブリック（共通10軸）

各項目を 1〜3 の3段階で評価する。

---

**[AA] 一次情報密度**

事業者本人しか言えないエピソード・判断基準・お客様反応の含有量を見る。Insight Cast の核は一次情報の引き出しと整え。書き出された記事に一次情報がどれだけ残っているかが核心。

| スコア | 基準 |
|---|---|
| 3 | 事業者本人しか言えない具体エピソード・判断・お客様反応が3件以上、本文中に明示されている |
| 2 | 1〜2件は入っているが、汎用的な記述が混じっている |
| 1 | 抽象論ばかりで具体エピソードがない。他社でも書ける一般的な内容 |

---

**[AB] 視点一貫性**

articleType ごとに守るべき視点を、最後まで崩さず維持できているかを見る。

| articleType | 視点 |
|---|---|
| client | 事業者本人の一人称（「私たち」「うち」など） |
| interviewer | 取材者（AIキャスト）の視点（「〜が印象的でした」「〜だということが分かりました」） |
| conversation | 二者の発話が会話バブルの形式に沿って維持されている |

| スコア | 基準 |
|---|---|
| 3 | 視点が冒頭から末尾まで完全に統一されている |
| 2 | 1〜2箇所で視点の揺れがある（client なのに「〜とのこと」「〜だそうです」が混入、など） |
| 1 | 複数箇所で視点が崩れている |

---

**[AC] 抽象表現の少なさ**

「丁寧」「安心」「信頼」「こだわり」のような抽象語で終わる段落がないかを見る。抽象語があってもよいが、必ず具体例とセットになっている必要がある。

| スコア | 基準 |
|---|---|
| 3 | 抽象語が出てきても、必ず具体的なエピソードや事例が伴っている |
| 2 | 抽象語のみで終わる段落が1〜2箇所ある |
| 1 | 抽象語の羅列で具体性が乏しい。「他のどこにでも書いてある」記事に見える |

---

**[AD] タイトル品質**

タイトルは検索結果・SNS・社内HP一覧で最初に見られる要素。これが弱いと中身が読まれない。

| スコア | 基準 |
|---|---|
| 3 | 30字以内 / 検索意図か感情フックを含む / 「〇〇のこだわり」など汎用語で終わらない / 事業者の特徴か視点が透ける |
| 2 | 条件のうち1〜2個を満たさない（30字超、フックが弱い、やや汎用的） |
| 1 | 「〇〇のこだわり」「私たちの想い」のような汎用タイトル。30字を大きく超過 |

---

**[AE] 抜粋品質**

抜粋は記事一覧・SNSシェア・検索結果のスニペットで使われる。150字内に記事の本質が圧縮されている必要がある。

| スコア | 基準 |
|---|---|
| 3 | 150字以内に「誰の・何の話・読むと何が分かるか」が3要素とも入っている |
| 2 | 要素のいずれかが弱い（誰の話か曖昧 / 価値が伝わらない / 内容紹介止まり） |
| 1 | 本文先頭の機械切り出しに見える / 内容が伝わらない / 文の途中で切れている |

---

**[AF] 構造整合**

H1・H2の並びと、各セクションが一論点に絞られているかを見る。AI検索や読者にとって「どこに何が書いてあるか」が分かることが引用価値に直結する。

| スコア | 基準 |
|---|---|
| 3 | H1が1個 / H2が論理的順序で並んでいる / 各セクションが一論点 |
| 2 | H2の並びに論理ジャンプがある / 一段落に複数論点が詰まっている |
| 1 | H1が複数または無い / 構造が崩れている / 見出しと内容がずれている |

---

**[AG] CTA・次の行動**

事業者HPで機能させるなら、記事末尾に自然な次の行動への橋渡しが必要。押し売りはしないが、無いと読者が次に何をすればよいか迷う。

| スコア | 基準 |
|---|---|
| 3 | 押し売りでない自然な次アクション（問い合わせ・予約・来店）への橋渡しが末尾にある。事業者の温度感に合っている |
| 2 | CTA はあるが押し売り的 / 唐突 / 取ってつけたよう / 事業者の文脈と噛み合っていない |
| 1 | CTA が無い / 記事が唐突に終わっている / 「ぜひお問い合わせください」だけの定型文 |

---

**[AH] 内部リンク活用**

内部リンク候補（自社HPの過去ブログ）が API に渡されているとき、その候補が本文中に自然に配置されているかを見る。

| スコア | 基準 |
|---|---|
| 3 | 候補から1〜3件が、文脈に合った形で本文中に配置されている |
| 2 | 候補があるのに使っていない / 不自然な位置に置かれている |
| 1 | 候補にないURLを勝手に作っている / 全く活用していない（候補ありの時） |
| N/A | 候補が渡されていないセッション |

---

**[AI] 一人称統一**

`owner_first_person`（プロフィール設定値）が指定されているとき、本文中の一人称が完全に統一されているかを見る。

| スコア | 基準 |
|---|---|
| 3 | 設定された一人称（例: 「うち」）で本文中が完全統一されている |
| 2 | 1〜2箇所で他の一人称（「私」「弊社」「僕」）が混ざっている |
| 1 | 複数箇所で一人称が混在している |
| N/A | `owner_first_person` 未設定のユーザー |

---

**[AJ] 文字数遵守**

volume 指定（short / medium / long / pillar）の範囲内に収まっているかを見る。指定上限を大きく超える記事は薄まり、下限を割る記事は内容不足。

| volume | 範囲 | スコア3 | スコア2 | スコア1 |
|---|---|---|---|---|
| short | 600〜800 | 範囲内 | ±20% 以内 | ±20% 超 |
| medium | 1200〜1500 | 範囲内 | ±20% 以内 | ±20% 超 |
| long | 2000〜2500 | 範囲内 | ±20% 以内 | ±20% 超 |
| pillar | 5000〜8000 | 範囲内 | ±20% 以内 | ±20% 超 |

## 3. 総合評価の目安

10軸の合計スコアで判断する。ただし [AH] / [AI] は N/A の場合があり、満点が変動する。

| [AH] | [AI] | 満点 |
|---|---|---|
| 該当あり | 該当あり | 30 |
| 該当あり | N/A | 27 |
| N/A | 該当あり | 27 |
| N/A | N/A | 24 |

| 割合（得点 / 満点） | 総合評価 | 対応 |
|---|---|---|
| 90%以上 | 高品質 | 良事例として記録。プロンプトのベースラインに |
| 65〜89% | 改善余地あり | 弱かった軸を AIデザイナー に共有。プロンプト改善候補に |
| 64%以下 | 要改善 | 原因分類のうえ AIデザイナー にて改善案を作成 |

**65% ライン**: 各軸が平均2点（10×2=20）が最低水準ラインに相当。1軸でも1点に落ちると 19 点になり要改善ラインに入る。`ai-cast-evaluation.md` 2-3節と整合。

## 4. 評価プロセス

### トリガー（いつ評価するか）

| トリガー | 説明 |
|---|---|
| 定期評価 | 月1回、直近1ヶ月に生成された記事から無作為に5件以上を抽出して評価 |
| 気になる記事 | ユーザーフィードバック・閲覧数の異常があった場合はその都度実施 |
| プロンプト改訂後 | 変更後の最初の5件を評価して効果を確認 |

### 誰が評価するか

| 役割 | 担当内容 |
|---|---|
| AIセルフ採点 | 記事生成直後に自動実行。`articles.quality_review.ai_self` に保存 |
| レビュアー | 月次抽出評価。本ルーブリックで人間採点を実施し、AI採点との乖離を確認 |
| AIデザイナー | 改善提案の作成・プロンプト改訂 |
| 人間（運営） | 最終判断・承認（ルーブリックの骨格変更、プロンプト大幅改訂） |

### 評価の流れ

```
1. レビュアーが対象記事を選ぶ（直近1ヶ月から5件以上、無作為抽出）
2. 各軸を 1〜3 でスコアリング
3. 低スコア項目に「なぜそうなったか」を1〜2文で記録
4. AIセルフ採点（articles.quality_review.ai_self）と比較し、乖離が ±1 を超える軸を抽出
5. 乖離が大きい軸はAIデザイナーに共有
6. AIデザイナーが原因分類を行い、プロンプト改訂案を docs/ai-specs/ に起案
7. 改訂は人間の確認後に反映
```

## 6. 改善ループへの接続

### AIデザイナーへの共有

レビュアーが評価レポートを作成した後、以下の形式で AIデザイナーに渡す。

- 弱かった軸（[AA]〜[AJ]）
- 弱さが出た具体的な箇所（記事の引用）
- 想定原因（プロンプトの書き方か、モデルの特性か、入力データの薄さか）

AIデザイナーは原因分類を行い、改善案を `docs/ai-specs/` に起案する。改善案は人間の確認後に `app/api/projects/[id]/article/route.ts` のプロンプトへ反映する。

### ルーブリック自体の改訂

運用を通じて「基準が現実と合っていない」と感じた場合、レビュアーが改訂案を作成し、AIデザイナーと確認のうえ人間に承認を求める。骨格の変更は必ず人間承認を得る。

## 7. 現時点での既知の評価上の注意点

- **記事の長さは品質と直接関係しない**。short でも [AA][AE] が3点なら高評価。pillar で長くなっても抽象語の繰り返しなら低評価。
- **業種によって一次情報の出やすさが違う**。差別化が語りにくい業種では [AA] の判断を緩める。その旨をコメントに記録する。
- **[AH][AI] は N/A の時に満点を下げる**（`ai-cast-evaluation.md` の [L][M] と同じ運用）。スコア0と混同しない。
- **AIセルフ採点と人間採点が ±2 以上ずれる軸はプロンプトの基準が甘いサイン**。AIデザイナーがセルフ採点プロンプトを改訂する。
- **conversation は [AB][AC] の判定が難しい**。会話体で抽象語が出やすいため、[AC] の判定はやや緩めにする（事業者の発話に出る抽象語は許容、インタビュアーの発話は厳しめ）。

## 8. AIセルフ採点との関係

`lib/article-self-review.ts` で実装される AI セルフ採点は、本ルーブリックの軸を入力プロンプトに含めて Haiku で実行する。出力 JSON は以下:

```ts
type ArticleSelfReview = {
  scores: {
    primary_info: number       // [AA]
    perspective: number        // [AB]
    abstract_density: number   // [AC]
    title_quality: number      // [AD]
    excerpt_quality: number    // [AE]
    structure: number          // [AF]
    cta: number                // [AG]
    internal_link: number | null   // [AH] N/A は null
    first_person: number | null    // [AI] N/A は null
    char_count: number         // [AJ]
  }
  total: number
  total_max: number
  weakest_axes: string[]       // ['perspective', 'cta'] など 1〜3 軸
  comment: string              // 弱かった点の具体（240字以内）
}
```

このスキーマは `articles.quality_review.ai_self` に保存され、admin 画面で可視化される。

## 9. レビュアーへの引き継ぎ

この設計書の初版を AIデザイナーが作成した。以後の運用・改訂はレビュアーが主担当となる。

引き継ぎ時の確認事項:
- 記事の抽出方法（Supabase から取得する方法はエンジニアに確認）
- 評価レポートの保存先 `docs/review-log/articles/` の作成
- 月次サマリーの保存先 `docs/review-log/articles/monthly/` の作成
- 最初の評価対象は、ドッグフーディング（自社取材）の記事が望ましい

特に見てほしい観点:
- スコア基準の「1〜3」が現場で判断しやすいか（曖昧な場合は補足例を追記する）
- AIセルフ採点との乖離が大きい軸が、プロンプト改訂で解消されるか

世界観チェック済み:
- 評価項目に「AI」「生成」「プロンプト」などのAI専門用語を顧客向けに使わないことを確認済み（本書は社内向けなので問題なし）
- 評価基準が「事業者の負担最小化」「一次情報優先」原則と整合していることを確認済み
